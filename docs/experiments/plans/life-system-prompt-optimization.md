# Plan: Optimize the `life` agent system prompt (latency + tokens, keep relevance)

## Context

Every turn of a Havaya app chat re-builds and re-sends `life`'s full system prompt — a **~30–34 KB static block** — to the model, with **no prompt caching**. ~90% of the bootstrap weight is two files (`AGENTS.md` 13.4 KB + `SOUL.md` 12.6 KB), and most of `AGENTS.md` is **irrelevant to app users** (Telegram memory lanes §3, group chats §2, projects/meta/temp §6–8). App sessions also receive framework sections they can't use (CLI quick-ref, self-update, heartbeats) and possibly a large bundled skills catalog. Net: we pay latency + tokens every turn for content the app user never needs, and re-pay it because nothing is cached.

Goal: cut per-turn latency + token cost for **app-user** sessions while preserving output quality. Hard constraint: **Telegram/owner sessions stay byte-identical** — and (per review below) this is now enforced *mechanically*, by routing every app change through app-only code paths and never editing shared on-disk files.

## Review response — Codex review 4533385398 (addressed in this revision)

- **[P1] Phase-1 host edits broke the non-app byte-identical gate.** Removed all on-disk edits to shared files. ALL app trimming now flows through the app-only `agent:bootstrap` hook + a new `"app"` PromptMode, reading **additive app-variant files** (`SOUL.app.md`, `AGENTS.app.md`). `SOUL.md`/`AGENTS.md` on disk are untouched → Telegram/owner load identical bytes. Empty/dup files are excluded **for app sessions only** (not deleted globally).
- **[P1] Skill scoping must be life-only/config-driven.** No longer edits the shared `buildAppSkillsPrompt`/`limitAppSkills` to hardcode life's skills. Instead a **per-agent, config-driven allowlist** (life's `openclaw.json`) is read by the shared code; default (no allowlist) = today's behavior, so other app agents keep their own catalog (asserted by test).
- **[P2] APP_PROFILE needs a real render split, not a hook reorder.** Adds a **dedicated app-profile render slot** in `buildAgentSystemPrompt` (its own section after `# Project Context`, just before `## Runtime`); APP_PROFILE is removed from the bootstrap-file list / Project Context. Tests assert it's absent from Project Context and appears exactly once after the shared prefix.
- **[P2] Compaction parity gate.** Verification now covers the compaction/manual-overflow path (`compact.ts`), mirroring the #74 lesson — not just the fresh-session path.

## Review response — Codex review 4536644504 (rev3 — implementation guardrails)

Rev2's four plan-level blockers were accepted as addressed. These three sharpen the implementation so the work can't drift global, skip a code path, or serve stale prompts. All three were re-verified against the live source (`/root/AgentGlob_Apps/openclaw`, `main`):

- **[P1] Allowlist must be per-agent, resolved by agent id — never global.** Confirmed: `limitAppSkills(skills, config?)` (`workspace.ts:578`) receives only `config`; the sole skills-*limits* schema (`config.skills.limits.maxSkillsInPrompt`, `types.skills.ts:31` / `workspace.ts:139`) is **top-level**, while per-agent `agents.list[].skills` (`types.agents.ts:29`) is just an enabled-list `string[]`. So a top-level `appAllowlist` would scope **every** app agent. Fix: the allowlist is a **new per-agent field** (`appSkills`, resolved for `sessionAgentId` the same way per-agent `skills`/`model` already merge — life sets it under `agents.defaults`, multi-agent configs under the matching `agents.list[]`). The **caller** (`attempt.ts`/`compact.ts`) resolves the agent-scoped allowlist and passes the resolved `string[]` into `limitAppSkills`; the shared helper stays config-shape-agnostic. **Wiring gotcha (verified):** `resolveSessionAgentIds` runs at `attempt.ts:446`, *after* the app-skills filter at `attempt.ts:308` — agent-id/agent-config resolution must be **hoisted above** the filter in both `attempt.ts` and `compact.ts`. Default (no `appSkills`) = today's behavior (test asserts a non-life agent's catalog is unchanged).
- **[P2] `compact.ts` is a first-class implementation target, not just a verification line.** Confirmed: `compact.ts:379–438` independently re-derives `appUserId`, `appSkills`, `appSkillLoad`, `skillsPrompt`, bootstrap context, and the system prompt — a near-verbatim mirror of `attempt.ts:308–390`. Fix: extract a **shared `resolveAppPromptContext` helper** (promptMode + `appUserId` + resolved app-skill allowlist + APP_PROFILE render input) consumed by **both** `attempt.ts` and `compact.ts`, so the `"app"` PromptMode, scoped skills, and the APP_PROFILE slot can't diverge across the two paths. `compact.ts` is now named in Critical files and in every relevant Phase 1/2 bullet.
- **[P2] Memoization needs invalidation/rollback semantics.** The per-session bootstrap memo (Phase 2.3) is a **new** optimization, so the staleness risk is self-inflicted: editing or rolling back `AGENTS.app.md`/`SOUL.app.md` (or the allowlist) must invalidate live sessions. Fix: memo **cache key = (sessionKey, promptMode, app-variant file mtime+size [or content hash], config version)**; any change misses the cache and re-resolves. Conservative fallback if hashing is deemed too costly: **new-session-only** memo (don't reuse across host edits) or a short TTL. APP_PROFILE + scoped skills stay **outside** the memoized span (name-on-message-1 preserved). *(`appSkills` schema/resolver mechanics corrected in rev4 below.)*

## Review response — Codex review 4536672313 (rev4 — `appSkills` schema + resolver)

One remaining [P1]: rev3's "life sets `appSkills` under `agents.defaults`" wouldn't work as written. **Verified against live source** — sharper than the review states:

- `resolveAgentConfig(cfg, agentId)` (`agent-scope.ts:99`) maps only the **`agents.list[]` entry** (via `resolveAgentEntry` → `listAgentEntries`, `:35/:94`) into `ResolvedAgentConfig` (`entry.skills` at `:116`); it **never merges `agents.defaults`**. Model only works because a *separate* resolver reads `cfg.agents.defaults.model` directly as a fallback (`:165–185`).
- `listAgentEntries` returns `[]` when `cfg.agents.list` isn't an array (`:36–39`), and **life's config is `defaults`-only** (`agents: { defaults: { model } }` — **no `agents.list[]`**, confirmed on the US host). So `resolveAgentConfig("life")` → `undefined`: reading `resolveAgentConfig(...)?.appSkills` would be **silently undefined for life**, and the agent-entry path is unavailable to it entirely.
- Both agent schemas are `.strict()` (`zod-schema.ts`), so an undeclared `appSkills` key is **rejected at validation**.

**Fix (now in Phase 2.2 / Critical files):** add `appSkills?: string[]` to **both** the agent-**defaults** type+schema (`AgentDefaultsConfig` / its `.strict()` zod object) **and** the agent-**entry** type+schema (`AgentConfig` / `AgentEntrySchema`). Add a dedicated resolver `resolveAppSkillsAllowlist(cfg, agentId)` returning **`entry.appSkills ?? cfg.agents?.defaults?.appSkills`** (entry overrides default) — mirroring the existing model/workspace defaults-fallback precedent (`agent-scope.ts:165–185`), **not** `resolveAgentConfig(...).appSkills` (undefined for life). For life (defaults-only) the **defaults path is load-bearing**; the entry path serves multi-agent configs.

## Recommended approach (phased)

### Phase 0 — Measure & answer the caching question (host env, zero-risk)
Set `OPENCLAW_CACHE_TRACE=1` for life, run a fixed **5-turn app-session script** against prod `life`; capture per-turn assembled-prompt **bytes/tokens**, **latency**, and **turn-2 `usage.cachedTokens`** (does Venice cache implicitly?). Also dump the actual app `<available_skills>` catalog size. Output: baseline table + implicit-caching yes/no (decides Phase 3).

### Phase 1 — App-only prompt slimming (openclaw PR → gateway image → roll life-only)
Every change here is **app-session-only**; shared on-disk files are never edited, so Telegram/owner prompts stay byte-identical.
0. **Shared `resolveAppPromptContext` helper (do this first).** Extract the app-session prompt logic — `isAppUserSession` → `"app"` PromptMode, `appUserId`, resolved app-skill allowlist, APP_PROFILE render input — into one helper consumed by **both** `attempt.ts` and `compact.ts`. Both files re-derive this today (`attempt.ts:308–390`, `compact.ts:379–438`); routing both through the helper is what makes the rest of Phase 1/2 land in both paths automatically (Codex 4536644504 #2).
1. **New `"app"` PromptMode** (`system-prompt.ts:15`; gated on `isAppUserSession` via the shared helper — replacing/extending the `attempt.ts:491` mode gate **and** its `compact.ts` mirror): drop `## OpenClaw CLI Quick Reference`, `## OpenClaw Self-Update`, `## Silent Replies`, `## Heartbeats`, `## Model Aliases`, `## Documentation`; **keep** Safety/Tooling/Tool-Call-Style/Skills/Memory/Workspace/Reply-Tags/Messaging/Voice.
2. **App-variant bootstrap files via the `agent:bootstrap` hook** (`bootstrap-hooks.ts`), app sessions only: substitute **`AGENTS.app.md`** (lean: behavior §1 + app_profile/save_user_section §4–5 + privacy §9 + Graphiti §1–2) and **`SOUL.app.md`** (persona + 5-stage method summary; the detailed exercise scripts live in the `personal-vision-exercise` skill, loaded on demand); and **exclude** `TOOLS.md`/`MEMORY.md`/`HEARTBEAT.md`/`IDENTITY.md`/`USER.md`. The `.app.md` variants are **additive** host files — originals untouched, so Telegram keeps full `SOUL.md`/`AGENTS.md` + inline exercises. The hook fires for both the run and compaction paths (it sits in shared bootstrap resolution), so no per-site wiring is needed here.

### Phase 2 — Per-user placement, config-driven skills, memoization (same PR/roll)
1. **Dedicated APP_PROFILE render slot:** add an `appProfileContext` input to `buildAgentSystemPrompt`, rendered as its own section AFTER `# Project Context`, immediately before `## Runtime`; stop appending `APP_PROFILE.md` into the bootstrap-file list (so the shared `# Project Context` is byte-stable/cacheable and APP_PROFILE sits after the cached prefix). The render input comes from the shared `resolveAppPromptContext` helper, so it's populated identically on the run **and compaction** paths. Preserve the #71 first-turn `appUserIdFromSessionKey` resolution.
2. **Per-agent app-skill allowlist (resolved by agent id, never global):** add a **new `appSkills?: string[]`** to **both** the agent-**defaults** type+schema (`AgentDefaultsConfig` + its `.strict()` zod object) **and** the agent-**entry** type+schema (`AgentConfig`/`AgentEntrySchema`) — both schemas are strict, so an undeclared key is rejected (Codex 4536672313). Add a dedicated resolver **`resolveAppSkillsAllowlist(cfg, agentId) = entry.appSkills ?? cfg.agents?.defaults?.appSkills`** (entry overrides default), mirroring the model/workspace defaults-fallback precedent (`agent-scope.ts:165–190`) — **not** `resolveAgentConfig(...).appSkills`, which is `undefined` for life (defaults-only, no `agents.list[]`). The **caller** (`resolveAppPromptContext`, used by both `attempt.ts` and `compact.ts`) calls this resolver and passes the resolved `string[]` into `limitAppSkills` — the shared helper stays config-shape-agnostic, so a top-level field can't accidentally scope all agents (Codex 4536644504 #1). **Required wiring:** hoist `resolveSessionAgentIds`/agent-id resolution **above** the app-skills filter (today `:446` runs after the `:308` filter) in both files. Absent `appSkills` = current behavior → other app agents unaffected (asserted by test). For life set it under `agents.defaults.appSkills` (the load-bearing path); multi-agent configs set it per `agents.list[]` entry. NOT `agents.list[].skills` (the enabled-list) and NOT top-level `skills.*`.
3. **Memoize shared bootstrap resolution per session** (`resolveBootstrapContextForRun`), keeping APP_PROFILE + scoped skills OUTSIDE the memoized span (name-on-message-1 preserved; memoized prefix stays byte-stable for caching). **Invalidation (Codex 4536644504 #3):** key the memo on `(sessionKey, promptMode, app-variant file mtime+size [or content hash], config version)` so editing/rolling back `AGENTS.app.md`/`SOUL.app.md` or the `appSkills` allowlist misses the cache and re-resolves; conservative fallback = **new-session-only** memo (no reuse across host edits) or short TTL. No silent staleness across an app-variant edit or rollback.

### Phase 3 — Caching (gated on Phase 0; owner decision if needed)
- If Phase 0 shows Venice **already caches** the stable prefix → Phase 1–2's stable-prefix work captures the win automatically.
- If **not** (owner decision, privacy/cost): **Option A** — generalize pi-ai's openai-completions `cache_control` injector behind a per-model flag and test whether Venice honors it (keeps Venice). **Option B** — route `claude-opus-4-6` to an Anthropic-API endpoint so the existing `cacheRetention` path works (cost + data-routing sign-off).
- Either way: 2 breakpoints — after the shared prefix (framework + app-variant bootstrap, shared across all life app users) and after the per-user block (APP_PROFILE + scoped skills).

## Expected impact
- App-session static prompt **~30–34 KB → ~12–16 KB** (lean app-variants + dropped framework sections + scoped skills + excluded empties). Telegram unchanged.
- With caching (Phase 3): stable prefix re-billed ~10% after turn 1 → large additional input-token + latency cut on multi-turn chats.

## Verification

- **Behavior parity (app):** fresh-session first "Hi" greets by name (#71); jail intact; `summaryskill` + `personal-vision-exercise` load via `load_skill` and run end-to-end in Hebrew; `save_user_section` + Graphiti recall intact; TAL persona/method preserved.
